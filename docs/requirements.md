# 需求分析

## 1. 项目背景

在校园生活中，校园卡、钥匙、雨伞、耳机、书籍等物品遗失的情况较为常见。目前，同学们通常在班级群、宿舍群或朋友圈中发布寻物、招领信息，但这些渠道覆盖范围有限，消息也容易被后续聊天内容覆盖。失主和拾取者即使发布了信息，也可能因为不在同一个群聊中而无法取得联系。

因此，本项目计划设计一款简单的“校园失物招领小程序”，将寻物和招领信息集中展示，并提供发布、浏览、搜索、查看详情和修改状态等功能，减少信息传播中的阻碍，提高物品寻找和归还的效率。

## 2. 主要用户及需求

| 用户类型 | 典型场景 | 主要需求 |
|---|---|---|
| 丢失物品的学生 | 在教学楼遗失校园卡，希望尽快找到 | 发布寻物信息、搜索招领信息、查看联系方式、将信息标记为已找回 |
| 捡到物品的学生 | 在食堂捡到雨伞，希望联系失主 | 发布招领信息、补充物品特征、等待失主联系、将信息标记为已归还 |
| 普通浏览者 | 浏览近期校园失物信息 | 按类型或分类浏览信息，帮助同学辨认或转发 |

用户希望用较少的操作完成发布和查询，因此页面应当简单直观，不要求用户学习复杂的操作方法。

## 3. 需要解决的主要问题

1. **信息分散：** 寻物和招领信息分布在不同群聊及社交平台，失主难以全面查看。
2. **消息容易被覆盖：** 群聊消息更新较快，较早发布的信息很难再次找到。
3. **缺少统一检索：** 用户无法直接通过“校园卡”“雨伞”等关键词查找相关信息。
4. **信息类型不清楚：** 寻物信息和招领信息混合发布，用户需要花费时间判断。
5. **状态更新不及时：** 物品找回后，原信息仍可能继续传播，造成无效联系。

## 4. 典型用户故事

- 作为一名失主，我希望发布物品名称、遗失地点和时间，以便拾取者能够辨认并联系我。
- 作为一名失主，我希望搜索与物品名称相关的招领信息，以便快速发现可能匹配的物品。
- 作为一名拾取者，我希望发布物品图片和拾取地点，以便失主确认物品。
- 作为一名发布者，我希望在物品找回或归还后修改信息状态，避免继续收到无效联系。
- 作为一名普通用户，我希望区分寻物和招领信息，并查看完整详情。

## 5. 功能需求

### 5.1 首页浏览

- 首页集中展示近期发布的信息；
- 支持切换“寻物信息”和“招领信息”；
- 可以按校园卡、钥匙、电子产品、书籍、生活用品和其他等类别查看；
- 信息卡片展示物品图片、名称、地点、日期、信息类型和当前状态；
- 点击信息卡片可以进入信息详情页。

### 5.2 发布信息

- 用户可以选择“发布寻物”或“发布招领”；
- 必填内容包括物品名称、分类、地点、日期、物品描述和联系方式；
- 物品图片为选填内容；
- 页面应对未填写的必填项进行提示；
- 点击“确认发布”后显示发布成功，并允许用户返回首页或查看自己的发布。

### 5.3 搜索信息

- 用户可以根据物品名称或描述中的关键词搜索；
- 支持按寻物、招领类型进行筛选；
- 支持按物品分类进行筛选；
- 搜索结果以信息卡片形式展示；
- 没有匹配结果时，应显示明确的无结果提示。

### 5.4 查看信息详情

- 展示物品图片、名称、信息类型和当前状态；
- 展示丢失或拾取的地点、日期和详细描述；
- 展示发布者提供的联系方式；
- 用户可以从详情页返回上一页面。

### 5.5 管理个人发布

- 用户可以在“我的发布”中查看自己发布的信息；
- 寻物信息可以从“寻找中”修改为“已找回”；
- 招领信息可以从“待认领”修改为“已归还”；
- 状态修改后，首页、搜索结果和详情页应显示最新状态。

## 6. 功能优先级

| 优先级 | 功能 | 说明 |
|---|---|---|
| P0 必须完成 | 首页浏览、发布寻物、发布招领、搜索、查看详情 | 满足作业要求和三条基本演示流程 |
| P1 建议完成 | 我的发布、修改信息状态、分类筛选 | 使信息能够形成较完整的使用闭环 |
| P2 暂不实现 | 即时聊天、地图定位、实名认证、智能匹配 | 实现成本较高，不属于本次作业重点 |

## 7. 非功能需求

### 7.1 易用性

- 首页、发布、搜索等主要入口应清晰可见；
- 同类按钮、标签和信息卡片保持统一样式；
- 用户完成发布和搜索时不需要经过过多页面；
- 必填项、发布状态和操作结果应有明确提示。

### 7.2 信息清晰性

- “寻物”和“招领”使用明显的文字标签区分，不能只依赖颜色；
- 地点、日期和状态应直接显示，方便用户快速判断信息是否相关；
- 已找回或已归还的信息应有明确的状态标记。

### 7.3 隐私与安全

- 只收集完成联系所必需的信息；
- 原型和博客示例不使用真实手机号、QQ号等隐私数据；
- 联系方式可以采用部分隐藏的示例形式，如 `QQ：12******34`；
- 用户只能修改自己发布的信息状态。

### 7.4 可实现性

- 页面数量和交互步骤保持精简；
- 数据字段保持统一，为第二次结对编程预留清晰的数据结构；
- 本次原型不依赖地图、聊天或复杂推荐服务。

## 8. 数据内容要求

每条失物或招领信息至少包含以下内容：

| 字段 | 是否必填 | 示例 |
|---|---|---|
| 信息类型 | 是 | 寻物／招领 |
| 物品名称 | 是 | 蓝色校园卡 |
| 物品分类 | 是 | 校园卡 |
| 地点 | 是 | 图书馆三楼自习区 |
| 日期 | 是 | 2026-09-23 |
| 物品描述 | 是 | 卡套为透明材质，背面贴有标签 |
| 联系方式 | 是 | QQ：12******34 |
| 物品图片 | 否 | 校园卡示意图 |
| 当前状态 | 系统默认 | 寻找中／待认领 |

## 9. 原型验收标准

完成的原型至少应满足以下要求：

1. 包含首页、发布信息页、搜索页和信息详情页；
2. 能从首页的信息卡片进入详情页；
3. 能完成选择信息类型、填写表单并进入发布成功页；
4. 能输入“校园卡”等关键词并展示搜索结果；
5. 页面能够清楚区分寻物和招领信息；
6. 信息详情能够展示地点、日期、描述、状态和联系方式；
7. 可在“我的发布”中演示将信息修改为已找回或已归还；
8. 在线原型链接能够在未登录设计工具账号的情况下正常查看。

## 10. 本次项目边界

为保证原型简单、流程清楚，并便于后续编程实现，本次不设计实名认证、即时聊天、地图定位、后台审核、消息推送、智能推荐、图像识别和线上支付等功能。用户通过发布者留下的联系方式自行联系，系统只负责信息的集中发布、展示和查询。
